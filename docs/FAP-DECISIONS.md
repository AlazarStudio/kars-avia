# ФАП — история решений и их причины

> Составлено 2026-08-21 как расширение [FAP-HANDOVER.md](FAP-HANDOVER.md). Источник — память проекта (полный ФАП-кластер: брейнштормы с владельцем, разборы созвонов с заказчицей, аудиты, замеры стендов) за июнь–август 2026.
> Формат каждого пункта: **решение → причина → что отвергнуто / какой замер это определил**. Даты указаны, где восстановимы.
> Зачем читать: половина «странностей» модуля — не случайность, а осознанный размен. Прежде чем «чинить» что-то из этого списка — знай, почему оно такое.

---

## 1. Стратегия: почему бэк ФАП не переписан

- **Не переписывать embedded→relational (21.07, подтверждено 04.08).** 15 composite-типов вплетены в монолит + гидрация + нотификации + magic-link PWA; Mongo + `db push` без папки миграций = многомесячный ручной риск при потере атомарности одного документа. Отвергнут полный рерайт, который владелец сам же и предлагал как вопрос.
- **При перепроверке два довода аудита НЕ подтвердились** (04.08): «миграционного прецедента нет» — есть (`migrateAirlinePriceGeographyToArray.js`), не хватает масштаба, а не прецедента; «движок стоимости = 150–250 строк» — занижено втрое. Направление сменилось на «сокращение объёма» (этапы 0–3), но не на рерайт.
- **Ключевой инсайт, освободивший от рерайта:** embedded-хранение не мешает считать деньги — экипажный движок стоимости работает чистыми функциями над row-объектами. Relations нужны только чтобы дотянуться до прайса. Настоящий пробел — **не смоделирована половина входов расчёта**, а не хранилище.
- **«Сохраняем функционал, а не поверхность API»** (04.08): операция может исчезнуть из схемы, если механизм её возможности назван. Отсюда план этапов 4–6 (55 → 42 мутации, адресация по id) — спланированы, не начаты.
- **Характеризационная сеть до первой удалённой строки** — решение владельца. 300+ тестов фиксируют поведение вплоть до порядка prisma-вызовов; критерий приёмки рефактора — «тесты не правились ни разу», а не число строк. Оценка экономии от конверта была завышена вдвое (факт 8–11% на модуль, не 30) — основную экономию дали предметные хелперы и таблица услуг; исполнители, отказавшиеся догонять ориентир ценой читаемости, были правы.
- **Конверт мутаций двухэтажный вынужденно**: полный `withPassengerRequest` не подходит четырём местам (отчёт пишет не заявку; delete; `$transaction`; create публикует сырую заявку) — хвост подходит всем.
- **Правило трёх шагов** (деплой всегда бэк → фронты): удаление из схемы не может ехать одним релизом с правкой клиентов. Селекция нового поля в `GET_PASSENGER_REQUEST` роняет всю деталку ФАП до деплоя бэка — проверено больно (`lunchboxCount`, `personId`, `submittedAt`).

## 2. Авторизация и доступ

- **Row-level, не содержимое** (04.08): режем только выдачу заявок; содержимое заявки (чужие гостиницы, реестр) владелец резать не захотел. Остаток называть остатком, а не считать закрытым. (Частично сужен пер-гостиничными гейтами 19.08.)
- **Сначала режим наблюдения, жёсткий режим отдельным релизом** — чтобы собрать лог реального трафика до включения. Перед флагом: `checkFapScopeReadiness.js` на бою + лог за рабочий цикл.
- **Ролевые middleware включать нельзя** — у `ExternalUser` нет поля `role`; любой `allMiddleware` кладёт PWA и гостиничный вход. Гейты — только через `resolveScope`.
- **Белый список типов субъекта закрытый** (`USER | EXTERNAL_USER | DRIVER | AIRLINE_PERSONAL`): проверка «субъект непуст» пропустила бы `HOTEL_PREVIEW` — держателя публичной ссылки-витрины — ко всем мутациям.
- **Семантика отказов не косметика**: аноним → 401 `UNAUTHENTICATED` (фронт считает восстановимым, тратит refresh, уводит на логин), чужой тип/мутация → 403; чужая заявка по id → `null`, не FORBIDDEN (иначе код ошибки подтверждает существование заявки).
- **`canSeeExternalLinks` — положительный список ролей, а не `!isAirlineRole`** (05.08): магик-ссылка — вход в чужую сессию, не поле данных, и она не одноразовая (при живой сессии повторный клик возвращает сессию). Осознанное следствие: гостиничные роли не видят кнопок копирования вообще, включая свою ссылку.
- **`reserveUpdateCompleted` — история разворота**: 12.08 — «COMPLETED правки не запрещает, отчёт дозаполняют после завершения»; 13.08 — «завершена = только просмотр, исключение — новое право». Дефолт `false` (владелец переставил на `true` и вернул обратно): право выдаётся осознанно; следствие выката названо явно — в день деплоя правка завершённых пропала у всех сразу. Гостиница по магик-ссылке заперта всегда — ей право выдать нечем (`accessMenu` у внешних нет).
- **Переоткрытие услуги** (06.08): только диспетчеры, причина обязательна, кнопка на всех услугах (а не только где дыра вылезла). Отвергнута существующая `setPassengerRequestServiceStatus`: `updateTimes` только добавляет отметки — услуга осталась бы «в работе» с датой завершения на карточке. Новая мутация лежит рядом с досрочным завершением, потому что обязана снимать ровно то, что оно ставит.
- **Гостиница видит только свою гостиницу** (12.08): под раздачу попадала внутренняя роль (вход по ссылке уже был ограничен). Инвариант — пара предикатов, а не одно сравнение: `null` у ограниченного = «не видно ничего»; голое сравнение склеило бы `undefined` с `undefined` и показало бы ровно ненастроенные гостиницы.

## 3. Деньги: отчёт проживания

### 3.1. Видимость отчёта авиакомпании

- **Отчёт открывается АК только по кнопке «Отправить на проверку»** (31.07): диспетчер контролирует момент готовности цифр; АК только смотрит — «никакого цикла согласования» (отвергнуто явно). Флаг по гостинице, не по заявке (готовность у гостиниц разная). XLSX прячется вместе с экраном — иначе гейт обходится выгрузкой.
- **Точек утечки было ШЕСТЬ, а не четыре** — включая серверный агрегат аналитики. Инвариант: любая правка видимости отчёта обязана проверять аналитику, клиентский гейт туда не достаёт.
- **Модель «отчёт живой, не снимок»** (05.08): из двух моделей выбрана вторая с оговоркой — изменение состава/размещения гасит отметку (бэк, `unsubmitReports` в конверте), отчёт возвращается к АК только повторной отправкой. Мигать не будет — владелец поправил формулировку сам.
- **Сброс отметки — только при реально изменившихся строках** (`reportRowsEqual`): автосейв дёргается флашем на unmount и перед Excel — без сравнения флаг слетал бы от захода в отчёт.
- **Бэкфилл истории обязателен** — иначе после деплоя все существующие отчёты, включая оплаченные, превратились бы в «Отчёт формируется».

### 3.2. Пиннинг цифр отправленного отчёта

- **Пиннится цена/вид размещения только у ОТПРАВЛЕННОГО отчёта** (05.08); у черновика пересчёт живой. Причина — замер: вся волатильная экспозиция (54 комнаты с видом размещения «из текущей занятости») сидела в отправленных отчётах. Безусловный пиннинг отвергнут: пришлось бы сбрасывать снимок в восьми местах = переписывание движка цены.
- **Вид размещения принадлежит НОМЕРУ, не гостю** — первая версия запиннила у гостя, и шапка разошлась с деньгами («Авто (одноместное)» над строками по 2-местному тарифу). `savedPlacementKind` не сбрасывать при «Применить всем» — пересчитало бы основание начисления всего номера, ровно тот сценарий, от которого пиннинг защищает (живой прецедент: комната сама переехала 2-местное → 1-местное, −6000 ₽).
- **`savedPricePerDay` сбрасывается при смене тарифа** (11.08): снимок принадлежит прежнему тарифу; смена тарифа осознанна, в отличие от чужих правок прайса.
- Порог `> 0` в обоих пиннингах несущий: бэк пишет `?? 0`, ноль = «нечем пиннить», а не «бесплатно».

### 3.3. Сутки

- **Сутки по длительности** (29.07, правило заказчика): минимум 1 + 0.5 за начатый 12-часовой блок. Скоуп — только ФАП; эскадрилью не трогать (`calculateEffectiveCostDays` жива ровно ради неё).
- **Разворот 05.08: ручная правка «Сут.» ДОЛЖНА сохраняться** — пересчёт при загрузке её затирал. Осознанный размен: сохранённый отчёт стал снимком по суткам.
- **Две формулы суток слиты в одну** (05.08, `fapPersonDays.js`) по слову владельца «уже решено, унифицируй» — до этого ФАП и представительский экран на одних данных давали 1 и 2 суток.
- **«Денежный баг getPersonDays» не подтвердился: 0 из 744 гостей** — главный замер кластера. Попутно вскрыто: ни один клиент не шлёт `movedAt`/`evictedAt` — все интервалы шахматки это серверные часы в момент клика, считать по ним деньги сомнительно по замыслу.
- **Выселенный выбывает из счёта совсем** (решение владельца 05.08, закрыто): ночи до выселения не оплачиваются. Замер под вопросом: из 58 выселенных 50 выселены в течение часа (ошибки), 8 реально прожили ~3 суток.

### 3.4. Режимы начисления и скидки

- **Режим — свойство тарифа** (`PER_BED`/`PER_ROOM`); режим номера задаёт «несущий» гость и применяется ко всем жильцам (первая по-гостевая реализация поймана ревью как шов неверного биллинга). При PER_ROOM возрастная скидка не применяется; показ «вся стоимость на несущем» заменён чипом на шапке номера по требованию владельца («только экран» — движок не трогали).
- **Скидка = колонка с дефолтами по возрасту** (взрослый 0 / ребёнок 50 / инфант 100), пусто = авто, явный 0 = «0%» — чтобы снимать льготу, не меняя категорию. Второго справочника льгот не заводили — выражена через существующий `accommodationChargeFactor`. **Скидки только на проживание** — питание не трогать по прямому указанию владельца.
- **Категория в отчёте не сохраняется** — берётся из живого `person.personCategory` (инвариант: строку отчёта расширять не надо).

### 3.5. Источники тарифа

- **Цены АК — третий, договорный источник** (30.07): тариф для пассажиров должен браться из договора с АК, а не из прейскуранта гостиницы. Незаполненная категория даёт «нет цены», гостиничная цена НЕ подставляется — иначе тихая подмена договорной цены нерелевантной.
- **Цены в отчёте не заморожены**: у гостя хранится только `tariffId`, цена берётся из живого источника при каждом открытии; ghost-строками персистятся только ручные тарифы. Договорный тариф предвыбирается только новым гостям.
- **Тарифы гостиницы показывают цену АК из-за старой инверсии** (03.07): флаг `...ForAirReq` означал «цена по запросу», а использовался как «использовать цену АК» — из-за этого АК видела договорные цены. Починено; но диспетчеру группа «Тарифы гостиницы» до сих пор отдаёт `priceForAirline` — задача «мы↔Объект» из задачника ещё не делалась (замер 21.08).
- **Дублирование тарифа по имени** (15.08): тарифы не хранятся объектами — восстанавливаются из строк; сравнение имён было асимметричным (`trim()` с одной стороны), а у 7 гостиниц из 24 имена видов с хвостовым пробелом. Решение — нормализованный ключ во всех 7 точках; миграция не нужна, мусор лечится сам. Опровергнуто «деньги потеряны» — потерь не было (маскировка режимом PER_ROOM); реально задето 3 строки.
- **Ланчбокс — три витка**: тумблер «разово на гостя» (22.07) → независимое количество `lunchboxCount` (28.07, «ланчбоксы независимы») → видимый янтарный ⚠ вместо молчаливого нуля + своё поле «Ланчбокс» у гостиничных тарифов (31.07). Решение владельца по истории: «пусть пересчитываются» — строки изменятся → автосброс отправки → диспетчер отправляет заново.

### 3.6. Прочее по отчёту

- **`personId` в строках отчёта** (22.07): матч по ФИО рвался при переименовании. Семантика: строка с `personId` матчится только по нему (удалённый гость не «крадёт» тёзку), без — по ФИО (legacy).
- **Предполётная проверка** (06.08): отчёт с нулевым итогом уходил АК молча. Правило метрики, купленное дорого: **считать по номерам, а не по строкам** — 353 «нулевые строки» оказались законными нулями соседей в PER_ROOM, 247 «без тарифа» — ручным вводом цены.
- **Экран ФАП v1 отчёта удалён целиком** (05.08, «экран вообще обсолет»): его сохранение стирало теневые строки тарифов, потому что бэк заменяет `reportRows` целиком, а таблицы цен видов размещения живут только там.
- **Реальные номера из фонда** (28.07): вид размещения берётся из категории номера, не из числа заселённых (подтверждено владельцем: 1 гость в 2-местном платит как за 2-местное); тариф не привязывается; занятость — подсказка, не блокировка.

## 4. Люди: идентичность, дубли, овербукинг

- **`personId` — канон идентичности реестра** (второй виток дедупа): ключ «по ФИО» сливал настоящих тёзок; ключ «ФИО+место» задваивал каталог (услуги пишут снимок без места). Размен: дважды вручную набранное ФИО = две записи. Слияние только через каталог.
- **Приоритеты слияния осознанно противоположны**: add-путь existing-wins (повторное добавление с дефолтом не затирает реальный CHILD), edit-путь incoming-wins.
- **Дубли ловим по ФИО, а не по personId** (03.08): сканер и ручное добавление personId не шлют — у одного человека в двух гостиницах два разных id, ловля по id бесполезна. Поэтому в UI «совпадает ФИО — проверьте», а не «дубль»; тёзки — принятые ложные срабатывания. **Место — уточнитель, а не условие** (06.08): замер перевернул идею «ФИО И место» — ни в одной из 38 коллизий место не было заполнено у всех.
- **Овербукинг разрешён** (03.08): план (`peopleCount`) — заказ, факт (`people[]`) — факт, система молча ничего не переписывает; ограничение снято всем и без потолка, первое превышение — через подтверждение. Порог считается **по итогу операции** (пачка, пересекающая порог, ловится). `peopleCount = 0/null` = «не задано», а не «мест нет». Попутно: перевыполнение плана больше не переоткрывает COMPLETED (задевает все услуги — иначе статус мигал бы).
- **Жёстких блоков в ФАП нет вообще** — ни на перебор, ни на «перевезено > мест», ни на чужой рейс манифеста: предупреждение + подтверждение. Это последовательная позиция владельца.
- **Массовые операции** (31.07): одно действие = один запрос — 50 поштучных мутаций замусоривали историю и уведомления необратимо. Параллелить нельзя по двум причинам: выселение `splice`-ит индексы (обработка по убыванию) и неатомарный read-modify-write всего массива. Поштучные мутации оставлены — их зовут PWA и легаси.
- **Узкая мутация `assignPassengerRequestHotelRoom`** вместо широкой: `updatePassengerRequestHotelPerson` затирал даты/категорию; грепом трёх репо подтверждено «мина, а не пожар» — но мина настоящая.
- **Инфанты из манифеста — разворот за день** (31.07): утром «безымянных не заводим» (потому что «это младенцы» оказалось выводом, а не чтением файла), вечером АК подтвердила расшифровку «РМ = инфант» → заводим записями `‹сопровождающий› (инфант)` — довод владельца: «дальше и не вспомнят, что было». Сопровождающий в имени первым — чтобы сортировка ставила инфанта под его взрослым.
- **Группы**: один человек — одна группа (v1); требование размещения — метка, «отчёт по факту», система не принуждает; `togetherLevel` хранится на бэке, но вся логика ворнингов — фронт, на деньги не влияет. Слово «уровень» из интерфейса убрано после вопроса владельца «что делает эта кнопка».
- **Фамилии скрипт-агностично** (28.07): движок женских окончаний молча не работал — боевые ФИО латиницей, а гейт стоял на кириллицу. Инвариант: любое сопоставление фамилий в ФАП обязано работать на латинице.

## 5. Услуги

- **Трансфер** (29.07): привязка поездки к гостинице — явная (фаззи-матч адресов отвергнут); «перевезено N» на водителе; **факт = max(список, transportedCount), именно max, не сумма** — скан водителя добавляет тех же людей; «перевезено > мест» — мягкая подсветка («несколько ходок»), не блок.
- **Автозавершение по «перевезено N» оставлено как есть** (18.08): ввод числа, добивающего факт до плана, сам завершает услугу — осознанное следствие правила 29.07, бэк не трогали.
- **Состав завершённой услуги открыт** (18.08): запрет был односторонним (добавить нельзя, удалить/переименовать можно) — правка достроила добавление до уже действовавшего поведения, а не ослабила правило. Запрет остался только на CANCELLED. Багаж не трогали: там `canAct` гейтит заодно деньги и тип ТС.
- **Багаж — модель развернулась за день** (27.07): от «поле в карточке» к «поездка со многими пассажирами, у каждого свои бирки и цена» — основание: в реальном реестре строка = пассажир, не поездка. Сумма поездки — производная (Σ цен пассажиров), патчем не принимается — защита от двух источников правды. Ручной ввод пассажира убран совсем (только из реестра) — долг «пополнять savedPassengers» закрылся сам.
- **Устойчивый id водителя** (27.07): индекс был зашит в трёх местах (URL, авто-email, localStorage PWA); молчаливый фолбэк `drivers[i] || drivers[0]` показывал чужую поездку — заменён явной ошибкой «ссылка устарела».

## 6. Реестр дефектов и аудиты: чему научились

- **Реестру задач нельзя верить**: из 21 пункта 14 описаны неточно (04.08); из 10 проверенных следом — неточны все 10 (05.08). Правило: перед починкой любого пункта перечитать код. Это же дважды касалось «верной» гипотезы владельца (18.08 — подтвердилась, но не полностью, и это меняло оценку правки).
- **Не-дефекты, которые чинить было бы вредно**: №10 («починка» открыла бы порчу дублями), №16 (конвенция всего репозитория), №18 (не баг — незакрытая фича пушей), «правка состава на завершённой» (сознательное решение с комментарием).
- **Метод, который повторяется**: находящий агент → адверсариальный проверяющий с заданием ОПРОВЕРГАТЬ → **замер по стенду до починки**. Замер дважды переворачивал приоритет; рублёвые оценки агентов выбрасываются («говорить в сутках»); свой счётчик тоже врёт, пока не разложен по причинам (28 «нулевых строк» = 27 законных PER_ROOM). Один проверяющий на линзу — мало (фаза опровержения 11.08 отработала слабо: 1 снятая из 24): проверяющий нужен на каждую находку.
- **Дорогие замеры-открытия**: Prisma подставляет `@default` composite-поля на ЧТЕНИИ (бэкфилл при смене дефолта не нужен — и «дефолт достаётся даром» было опровергнуто зондом); `updateTimes` уже проставленную отметку не трогает (второе самоопровержение); скаляр `Date` сквозной, резолвера нет — `new Date(true)` прошёл бы как дата; фантомное поле `statusTimes.createdAt` сидело в 44 местах девяти тестовых файлов — заведён сторож фикстуры против схемы.
- **⛔ Закрыто владельцем, не поднимать**: валидация сайдбара услуг (замер: населённость нулевая — 9 из 133, все багаж и не из этой формы; а «вернуть `isFormValid`» заблокировало бы сценарий выключения услуги — тело писалось для другого сайдбара); выселенные вне счёта; last-write-wins отчёта («пока не делать»); D3-срез аналитики per-passenger («в принципе не нужно»); полиш-пакет аналитики.

## 7. Продуктовые решения заказчицы (созвоны)

- **08.07**: тариф = наименование (ссылка на ДС) + цена за сутки, проживание = цена × сутки; терминология «вид размещения» (1/2-местное, от фактического заполнения) vs «категория номера» (класс); койко-место в 1-местном ≠ в 2-местном; дети 2–12 — 50%, до 2 — 100%, единое по договорам.
- **03.08**: порядок работ — сначала электронный реестр эскадрильи, потом конструктор исчислений (сутки/ранний-поздний/час; часовая тарификация нужна под АК «Россия»); пока цены не разнесены, АК видит реестр без цен; «Питание и напитки в АП» — позже.
- **04.08**: ЛК гостиницы должен показывать сторону гостиницы, а не диспетчерско-авиакомпанейскую (контакты объекта, свои цены, без тарифов АК и чужого трансфера) — закрыто большей частью 19.08.
- **07.08 — ЛК пассажира** (концепт, к октябрю; полный разбор `docs/superpowers/2026-08-21-passenger-lk-call-2026-08-07-study.md`): один универсальный QR + ввод номера рейса; временный PWA-кабинет 48ч с автопродлением; ваучер с QR сканирует админ гостиницы; апгрейд категории — доплата **только на ресепшене, не через нас** («не создавать себе проблем»), галка-согласие = юридическое «претензий к АК не имею»; **чата не будет** («иначе заебут диспетчеров» — только горячая линия); **постоянного ЛК не будет** — принципиально: после закрытия ситуации доступ гасится, «чтобы не выкачал информацию и не пошёл по судам»; логинов/паролей нет; дубли повторных пассажиров недопустимы; сверка с манифестом обязательна, ФИО латиницей как в билете (автотранслитерацию делать не стали).

## 8. Развилки, открытые осознанно (знать, не «чинить» мимоходом)

1. **Номер комнаты — два взаимоисключающих правила** в `FapHotelPage` (строка отчёта побеждает при загрузке vs `person.roomNumber` — источник при синке), оба с комментариями. Владелец: «оставить как есть». Замер снял приоритет: все 16 расходящихся отчётов — черновики. Старые 196 строк не лечить — это переписало бы чужие отчёты.
2. **Ручной вид размещения при договорном тарифе** — два осознанных правила (docstring против docstring), денег не теряется.
3. **Серверная проверка прав редактирования** — вопрос владельцу о границах открыт (только завершённые / плюс reserveUpdate / вся модель для внешних).
4. **Дубль при повторном импорте манифеста после переименования** — следствие принятого правила «сшивка по ФИО»; альтернатива — новое правило, а не починка.
5. **`upsertSavedPassenger` и тёзки** — лечение дублей в корне упирается в вопрос «что делать при нескольких тёзках в реестре», не отвечен.
6. **Пиннинг не покрывает** сматчившийся с фондом номер другой вместимости (кейс −6000 до отправки) — владельцу названо, решение прежнее.
7. **`updatePassengerRequestHotel` не проверяет внешнего** — гостиница по ссылке может переписать план/имя/адрес; сообщено, не закрыто.
