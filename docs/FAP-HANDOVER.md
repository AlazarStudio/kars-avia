## 1. Что это и где живёт

**ФАП** — заявка на услуги пассажирам задержанного рейса: вода, питание, проживание в гостиницах, трансфер (прилёт/вылет), доставка багажа. Полное описание домена — FAP.md §1–2.

| Репозиторий | Роль | Ветка | Деплой |
|---|---|---|---|
| `kars-avia-backend-graphql` | GraphQL-бэк (Node, Prisma + MongoDB) | **main** (dev-ветки нет; dev отстаёт — так задумано) | дев: `devbackend.karsavia.ru`, прод: `backend.karsavia.ru` |
| `kars-avia` (CRM) | Фронт диспетчера/АК/гостиниц, модуль `src/Components/Blocks/FapV2/` | dev2 | `dev.karsavia.ru` |
| `RepresentativePWA` | PWA представителей/водителей (сканер посадочных, заселение) | main | отдельный деплой |

**Порядок деплоя всегда бэк → фронты.** Отсюда правило трёх шагов для любого изменения контракта: бэк добавляет новую форму → клиенты переезжают → бэк сносит старую. Ломать схему одним релизом нельзя.

**База — MongoDB, миграций нет (`prisma db push`).** Схему менять только аддитивно. Клиент Prisma генерируется в `./generated/client` (не в node_modules); без `npx prisma generate` любой скрипт падает. Локальный `.env` бэка смотрит в `mongodb://localhost:27017/avia-db` — это НЕ дев-стенд, для экспериментов безопасно.

- **`serviceTable`** — семь услуг одной таблицей; ⚠️ поля `empty` ≠ `statusFallback` — сводить нельзя, изменится записываемый документ.
- Статусы услуг: `recomputeServiceStatus` (`serviceStatus.js`) — чистая функция, ~21 вызов; **факт трансфера = max(поимённый список, `transportedCount`)** — ввод числа, добивающего факт до плана, сам завершает услугу (это осознанное поведение, решение владельца 18.08). У багажа `transportedCount` не заполняется — похожие reduce НЕ сводить с трансферными.

## 3. Авторизация — где мы сейчас

Подробно — FAP.md §3.3. Краткая карта:

1. **Аутентификация закрыта** (этап 0): `withFapAuthGuard`, белый список субъектов `USER | EXTERNAL_USER | DRIVER | AIRLINE_PERSONAL`. Аноним → 401, чужой тип (в т.ч. публичный `HOTEL_PREVIEW`) → 403. Различие 401/403 не косметика: фронтовый `authErrorLink` считает `UNAUTHENTICATED` восстановимым и уводит на логин.
2. **FAP_SCOPE (изоляция заявок между организациями)** — реализован, работает в режиме **наблюдения**: правила `fapScope.js`, охрана `fapScopeGuard.js`, лог `FAP_SCOPE` в `logs/warn/`. Включение жёсткого режима = env `FAP_SCOPE_ENFORCE=true`. **Перед включением обязательно**: read-only `services/migrations/checkFapScopeReadiness.js` на бою + лог за полный рабочий цикл (записи `unknown-role:*`/`unknown-scope:*` = стоп). Тесты уже сходятся в обоих режимах. Гостиничные субъекты изолируются безусловно, без флага.

   Правила `resolveScope` по субъектам (кто что видит):

   | Субъект | Скоуп | Правило |
   |---|---|---|
   | USER: диспетчеры (SUPERADMIN, DISPATCHER*) | всё | не ограничены |
   | USER: AIRLINEADMIN/MODERATOR, AIRLINE_PERSONAL | `airlineId` | только заявки своей АК |
   | USER: HOTELADMIN/MODERATOR/HOTELUSER, EXTERNAL scope HOTEL | `hotelId` | только заявки, где их гостиница выбрана в проживании (фильтр `livingService.hotels.some.hotelId`); изоляция безусловная |
   | EXTERNAL scope DRIVER | `passengerRequestId` | только своя заявка |
   | EXTERNAL scope REPRESENTATIVE | `airlineId`+`airportId` | пара АК↔аэропорт |

   Отказы: список молча фильтруется; чужая `passengerRequest(id)` → `null` (не FORBIDDEN — иначе код подтверждает существование); мутация → 403. Фильтр подмешивается в `where.AND`, не в корень (в корне уже лежит AND под поиск). Подписки проверяют скоуп **в `withFilter` на каждом событии** — одноразовой проверки при subscribe мало.
3. **Внутризаявочные гейты гостиниц** — коммит `e5ee1f9` (19.08): пер-гостиничные проверки в `living`/`livingMove`/`report`/`fields`/`subscriptions`, роль `HOTELUSER` в гостиничных ролях, аналитика «Пассажиры» гостиницам запрещена. Образец гейта — `assertHotelScopeAccess` (`livingHelpers.js`).
4. ⚠️ **Ролевые middleware включать нельзя** — у `ExternalUser` нет `role`, упадёт PWA и гостиничный вход. Только скоупы.
5. **Дыры, которые ещё открыты**:
   - серверной проверки прав редактирования нет: `reserveUpdate`/`reserveUpdateCompleted` — чисто фронтовые гейты, прямой мутацией завершённую заявку править можно. Точка перехвата готова (конверт), прецедент enforcement по accessMenu есть (`services/access/assertCanManageAccess.js`). Открытый вопрос владельцу: что именно запирать (только завершённые / плюс reserveUpdate у внутренних / всё правило с моделью доступа для внешних);
   - заявка отдаётся клиенту целиком (реестр, соседние гостиницы, выселения) — фильтрации содержимого документа нет;
   - `logaction.js` пишет `userId: null` для действий EXTERNAL_USER (история без автора) — файл общий на восемь модулей, **чужая зона**, самому не править, только сообщать владельцу.

## 4. Внешние пользователи и магик-линки

- Модели: `ExternalUser` (email @unique, `scope: HOTEL|DRIVER|REPRESENTATIVE`, `accessType: CRM|PWA`, привязки `hotelId/airlineId/airportId/passengerRequestId`, `sessionExpiresAt`) + `ExternalUserMagicLinkToken` (sha256-хэш, одноразовый). TTL ссылки и сессии — 48 ч (`services/auth/externalMagicLink.js`).
- Автосоздаваемые учётки: `hotel-{hotelId}@auto.internal`, `representative-{airlineId}-{airportId}@auto.internal`, `driver-{requestId}-{serviceKind}-{driverId}@auto.internal` (`services/auth/externalAutoLinks.js`).
- ⚠️ `PassengerServiceDriver.id` — **uuid v4, не ObjectId**; писать его в `ExternalUser.driverId` (@db.ObjectId) нельзя — Prisma падает, а `catch` в трансфере молча обнуляет `linkPWA`. Принадлежность водительской учётки несёт `passengerRequestId`.
- ⚠️ Магик-линк одноразовый: погашение ставит `usedAt` и **ротирует refreshToken** — живую ссылку гостиницы «проверить» нельзя, сожжёшь. Тестовую выпускать через `createExternalAuthLink` (upsert по email).
- Известный мусор: на дев-стенде живёт тестовый `ExternalUser` `stage3-check@karsavia.invalid` (scope HOTEL, «Азия») — мутации удаления внешнего пользователя в схеме нет, чистить руками в базе.

## 5. Тесты — сеть, на которой всё держится

`node --test tests/` — **814 тестов (замер 21.08), из них 300+ характеризационных** (`tests/passengerRequest/characterization/`): они фиксируют текущее поведение вплоть до порядка prisma-вызовов и полей лога. **Критерий любого рефактора: характеризационные тесты проходят без единой правки.** При починке дефекта — наоборот: тест, закреплявший дефект, обязан измениться, и ровно он один.

Ловушки прогона (все стоили времени): два падения — средовые и чужие (`tests/airline/`, `tests/geo/`, Node 20 без `mock.module`) — не чинить, бэйзлайн мерить «не выросло»; `releasePubsubAfterTests()` обязателен в каждом файле, импортирующем резолвер (иначе Redis-клиенты вешают раннер); прогон под `FAP_SCOPE_ENFORCE=true` обязан давать те же числа; поле плана — `peopleCount`, не `count`; новые тесты проверять красными со снятой правкой; локальный прогон пишет шум в боевой `logs/`.

Оснастка: `tests/helpers/prismaDouble.js` подменяет модели на синглтоне `prisma` (71 модель, все writable). ⚠️ Двойник по умолчанию **игнорирует `select`** — дефекты класса «поле не выбрано в select» на нём не воспроизводятся, нужен оверрайд `findUnique` (см. `fapScopeAuthContext.test.js`).

## 6. Почта и побочные эффекты

- Конверт шлёт письма участникам **по умолчанию**; `skipEmail: true` стоит ровно у трёх мутаций (`addPassengerRequestSavedPeople`, `updatePassengerRequestDriver`, одна в багаже). На дев-стенде почта ВКЛЮЧЕНА — любая «проверочная» мутация может разослать письма живым людям.
- Безопасный зонд конверта: `addPassengerRequestSavedPeople` с уже существующим ФИО (дедуп → «добавлено 0», документ не меняется, конверт проходится целиком).
- Мутации отчёта для зондов не годятся: маппер строк неидемпотентен (повторное сохранение удваивает вид номера).
- В dev-режиме `EMAIL_ENABLED !== "true"` глушит отправку, а `NODE_ENV=dev` редиректит всё на `EMAIL_RECEIVER`.

## 7. Инварианты — не ломать

1. `recomputeServiceStatus`: `CANCELLED` не трогаем; `COMPLETED` + новый человек → `IN_PROGRESS`; факт ≥ план → `COMPLETED`. Задевает ВСЕ услуги.
2. Правило «Σ мест ≤ план» и замки вместимости **сняты осознанно** (03.08, овербукинг) — не возвращать.
3. Гидрация идентичности: `savedPassengers` — канон; чтение накладывает реестр на услуги, запись пропагирует services → реестр (incoming-wins), добавление — снапшот в реестр (existing-wins для `personCategory`). Выселения и отчёты — снапшоты, гидрацией не трогаются.
4. Отчёт по отелю: тарифы сериализуются **ghost-строками** (пустой `fullName`); резолвер подменяет `roomCategory` на `makeRoomCategoryLabel(...)`; ghost-строки исключать из любых сумм по людям.
5. `hotelIndex`/`driverIndex`/`personIndex` — позиционная адресация массивов; удаление элемента сдвигает индексы соседей. Переход на id — отложенные этапы 4–6.
6. Окончания строк в обоих репо разнородны ПОФАЙЛОВО (CRLF/LF/mixed) — сохранять состояние конкретного файла, git-нормализация прячет это в диффах.
7. Фронт много где хранит деньги строками, и `null` ≠ 0 (`pricePerDay: null` не подменять нулём).

## 9. Правила работы, принятые в проекте

- Git-историю ведёт владелец: коммиты короткие, английские, только заголовок; коммит на дефект.
- Пайплайн изменений: брейншторм → спека (`docs/superpowers/specs/`) → план (`docs/superpowers/plans/`) → реализация; обе папки в .gitignore CRM-репо.
- В бэке чужие зоны (цены, география, `logaction.js`, транспортный модуль) — не править, только сообщать.
- Ни один источник задач не брать на веру: реестр дефектов ошибался во всех проверенных пунктах, задачник заказчицы — формулировки со слов; перед починкой мерить код и стенд.
- Стенд: дев-бэк `https://devbackend.karsavia.ru/graphql`; пара окружений переключается руками в `graphQL_requests.js` (первые 12 строк) — проверять, не помнить. Прод-бэк с закрытой интроспекцией: наличие поля меряется различающим зондом по разнице ошибок.
